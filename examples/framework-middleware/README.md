# Framework Middleware

> **Runs against the local SDK checkouts until the KYA-OS SDKs are published.**
> The code uses the KYA-OS APIs of `@helixid/sdk-js`, `@helixid/langchain`
> and `@helixid/mcp-middleware` (request proofs, the local verifier,
> `POST /v1/agents` onboarding); the published versions this package pins
> predate them, so it stays out of `workspace:typecheck` and its pins move
> with the release. In the local workspace, `pnpm e2e:setup` in
> e2e-playwright links the sibling checkouts.

This example shows the real HelixID LangChain and MCP adapters against a live
helixid, with nothing mocked: an agent with its own key, a KYA-OS request
proof on every MCP request, and a service that verifies it in-process.

## Who needs what

| Who | Does what | Needs |
| --- | --- | --- |
| Platform operator | Runs `setup-live.ts` once: registers the service, creates the agent, roots its authority over the service | Running helixid, admin key |
| Agent developer | Wraps tools with `HelixIDToolWrapper` (LangChain) or signs with `kyaos.withRequestProof` | The agent's signing key (from `helix init`), its chain, the service DID |
| Service developer | Puts `helixidMCPMiddleware` with `createLocalVerifier` in front of its tools | Its own DID and the tool → scope map |

The agent's private key is generated by `helix init` on the agent's machine
and never sent; helixid holds no agent keys (self custody, story F-3). The
service needs no Helix API call to verify: it reads DID documents, cards and
status lists from their publishers (story F-2).

## Run

Start helixid with the root environment loaded:

```sh
set -a; source .env; set +a
pnpm --filter @helixid/api dev
```

In a second terminal, with the same `HELIX_ADMIN_API_KEY` (and `HELIX_API_URL`
if the API is not on `http://localhost:3000`):

```sh
pnpm example:middleware:setup      # once
pnpm example:middleware:langchain
pnpm example:middleware:mcp
```

## What each script shows

- `setup-live.ts` registers a service (`POST /v1/services`), creates a
  self-custody agent (`POST /v1/agents`) and runs `helix init` for it into
  `agent/` (`did.json`, `card.json`, `signing-key.env`), then issues one root
  hop over the service (`POST /v1/grants`, the agent's delegation chain). It
  records the agent's DID, key id, key file, service and chain in
  `agent/agent.json`. `agent/` is ignored by Git.
- `langchain.ts` wraps an orders tool with `HelixIDToolWrapper`: the tool signs
  the MCP request it sends with `signCurrentRequest`, a fresh request proof
  with the chain attached, and the orders server's `helixidMCPMiddleware`
  verifies it (L3, the agent's scopes). A second tool asking for
  `write:inventory`, which the chain does not cover, is refused.
- `mcp.ts` signs `tools/call` requests with `kyaos.withRequestProof` and runs
  them through `helixidMCPMiddleware.authorize`: allowed for `read:orders`, the
  same request again refused (`nonce_replayed`), and `write:inventory` refused
  (insufficient scope).

## Environment

- `HELIX_API_URL` (or `API_BASE_URL`): helixid, default `http://localhost:3000`
- `HELIX_ADMIN_API_KEY`: the API admin key (setup only)

Against a local helixid the verifier reads http on loopback and binds the
Helix issuer to its identity status list, the list every hosted card names
(SPEC-ENTITY-CARD §10.3).
